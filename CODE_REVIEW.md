# Code Review

**Scope:** entire codebase (`src/`, `src/models/`, helper/build/packaging scripts, Debian packaging)
**Date:** 2026-07-28
**Verdict:** Solid overall — the root-elevation path (`Cmd`, `helper.cpp`, `mxpi-lib`/`mxpi-maintenance`) is carefully hardened and clean, but one confirmed shell command-injection bug exists in the unprivileged apt/aptitude preview path, plus several smaller correctness bugs.

## Action items

1. - [x] **Command injection via unquoted package names in `confirmActions()`** — `src/mainwindow.cpp:1923-1927`
   `detailedNames = cmd.getOut(frontend + aptget + action + ' ' + recommends + target + reinstall + names + awkFilter)` and the following `aptitude` call both concatenate `names` directly into a string run via `/bin/bash -c` (`Cmd::run`/`getOut(QString)`), with no `shellSingleQuote()`/`shellCommandFromArgs()` — unlike every other shell-string call site in this file. `names` comes from `changeList.join(' ')`, whose entries are package names parsed verbatim from `Package:` lines in `/var/lib/apt/lists/*_Packages` (`AptCache::parseFileContent()`, `src/aptcache.cpp:124-167`) with no character validation. A `Packages` index (e.g. from an enabled MX-Test/Backports repo or any third-party source) containing `Package: foo; touch /tmp/pwned #` gets shown as a selectable row; checking it and clicking Install/Uninstall executes the injected shell command as the local user, before the confirmation dialog is even shown. Fix by quoting `names` the same way `displayPackageInfo()` already does (`shellSingleQuote`/`shellCommandFromArgs`), or validate package names against `isValidPackageName()` (`src/packagelistparser.h`) when parsing the index.

2. - [x] **`VersionNumber::compare()` returns "not equal" for versions differing only by a trailing/embedded empty digit group** — `src/versionnumber.cpp:131-183`
   `groupDigits()` omits a digit run entirely when none is present (e.g. `groupDigits("1.")` = `["1","."]`, vs `groupDigits("1.0")` = `["1",".","0"]`), and the length-mismatch tail check (lines 176-179) treats any leftover component as making that side unconditionally bigger (barring `~`). Per dpkg's version-comparison rules, a missing trailing digit run is equivalent to an explicit `"0"`, so `dpkg --compare-versions 1.0 eq 1.` succeeds, but this code reports `"1.0"` as strictly greater than `"1."`. Any upstream/package version string ending in (or containing consecutive) non-digit separators with no trailing digit will be mis-ordered, which can make `AptCache::updateCandidate()` pick the wrong "newest" version or the app report a spurious available update. Fix by treating a missing digit run as an implicit `"0"` (append a placeholder in `groupDigits()`, or special-case it in the tail-comparison logic) instead of assuming "longer = newer".

3. - [ ] **`isLibraryPackage()` regex hides real, non-library packages whose name starts with "libre"/"lib"** — `src/models/packagefilterproxy.cpp:138-146`
   The regex `^lib(?!reoffice|rewolf)` only exempts names starting exactly with `libreoffice` or `librewolf` from the "hide libraries" filter. Any other real package starting with `lib`/`libre` — e.g. `librecad`, a genuine user-facing CAD application — matches the hide pattern and is silently removed from the Enabled/MX Test/Backports lists whenever "hide libraries" is checked (the default). The user has no way to find such a package except unchecking the filter entirely, which also un-hides all real libraries. Fix by anchoring the heuristic on library-specific suffixes/soname patterns rather than a bare `lib`/`libre` prefix, or maintain an allow-list of known non-library `lib*`-named apps.

4. - [ ] **`HELPER_INSTALL_DIR` is not actually wired through to the Debian package** — `debian/install:9`, `CMakeLists.txt:99-104,293-295`
   `CMakeLists.txt` added a configurable `HELPER_INSTALL_DIR` cache variable (default `/usr/libexec/mx-packageinstaller`) that's baked into the GUI binary as `HELPER_PATH` (`src/cmd.cpp:41`) and into the generated polkit policy, with `install(TARGETS helper RUNTIME DESTINATION ${HELPER_INSTALL_DIR})` (`CMakeLists.txt:293-295`). But `debian/install` still hardcodes the packaged destination as a literal string: `obj-*/helper   usr/libexec/mx-packageinstaller`, copied straight from the ninja build directory rather than derived from the CMake variable. It only "works" today because the literal happens to match the current default. If `debian/rules` is ever updated to pass a different `-DHELPER_INSTALL_DIR=...` (the exact scenario this option exists for), the compiled binary and policy file would point pkexec at a path where the helper binary was never actually installed, breaking every privileged operation (install/remove, Flatpak/Snap setup) in that build. Fix by deriving the packaged path from the same CMake variable (e.g. via a generated install manifest or `dh_auto_install`'s normal `debian/tmp` merge) instead of a second hardcoded string.

5. - [ ] **`pushForceUpdateFP_clicked()` silently ignores a failed flatpak appstream update** — `src/mainwindow.cpp:5165`
   `cmd.proc("flatpak", {"update", "--appstream"});` discards the return value and unconditionally proceeds to `displayFlatpaks(true)`. Every sibling "Force Update" handler for the APT tabs, and `pushUpgradeFP_clicked`/`pushRemoveUnused_clicked` for Flatpak, check success and show `QMessageBox::critical` on failure. A user clicking "Force Update" on the Flatpak tab while offline gets no error indication at all — just a silent re-display of the stale list. Add the same success check and error dialog used elsewhere.

6. - [ ] **`ManageRemotes` dialog leaks on every "Manage Remotes" click** — `src/mainwindow.cpp:5325`
   `auto *dialog = new ManageRemotes(this, fpUser); dialog->exec();` — the dialog is never deleted (no `deleteLater()`, no `Qt::WA_DeleteOnClose`). Being parented to `this` only guarantees cleanup at `MainWindow` destruction, so each invocation during a session leaks one live `QDialog` and its child widgets until the app exits. Add `dialog->setAttribute(Qt::WA_DeleteOnClose)` or an explicit `delete dialog;`/`std::unique_ptr` after `exec()`.

7. - [ ] **Non-CSI ANSI escape sequences are only partially stripped in the Output tab renderer** — `src/outputrender.h:156-158`
   `consumeEscape()` only recognizes `ESC [ ... letter` (CSI) sequences; for any other escape (e.g. an OSC sequence `ESC ] 0 ; title BEL`, or a charset-select `ESC ( B`) it returns immediately, dropping only the bare `ESC` byte while leaving the rest of the sequence (`]0;title`, `(B`, etc.) to be written into the output box as literal text. Any tool piped through this renderer that emits a non-CSI escape will show garbage characters in the Output tab instead of having them stripped. Extend `consumeEscape()` to recognize and discard at least the common OSC (`ESC ]`, terminated by BEL or `ESC \`) and single-character escape forms.
